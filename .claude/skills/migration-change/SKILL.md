## Context

Fixed facts about how migrations work in this repo:

- Alembic script location is `migrations/` (see `alembic.ini`), with revisions in
  `migrations/versions/`. Current head is `0009_bottle_processing_stage`; revisions are a single
  linear chain named `NNNN_snake_case`.
- `migrations/env.py` reads the URL from `config.attributes["database_url"]`, falling back to
  `Settings.from_env().database_url`, and configures with `render_as_batch=True` — required for
  SQLite ALTER support.
- `bourbonbook/migrations.py` owns the startup bootstrap:
  - `BASELINE_REVISION = "0001_current_schema"`, `HEAD_REVISION`, and `EXPECTED_SCHEMA`
    (the exact table→column sets of the recognized pre-Alembic legacy database).
  - `bootstrap_database(settings)` branches three ways: `alembic_version` present → `upgrade head`;
    no app tables → `upgrade head`; app tables exactly matching `EXPECTED_SCHEMA` → `stamp` baseline
    then `upgrade head`. Anything else raises `MigrationBootstrapError`.
  - It runs at app startup and explicitly at container startup before Uvicorn.
- `make pr-check` (`scripts/pr_review.py`) fails the build if `uv run alembic heads` reports more
  than one head, and it runs `tests/test_migrations.py` on its own.
- The database is SQLite with foreign keys enforced, WAL, and a busy timeout; production runs a
  single Uvicorn worker.

## Procedure

### 1. Decide whether a revision is required

Any change to `bourbonbook/models.py` that alters a table, column, index, constraint, or default
needs a revision. A pure Python-level change (a property, a validator, a relationship `lazy=` hint)
does not. When unsure, generate a revision and inspect it — an empty autogenerate body means no
schema change.

### 2. Write the revision

```bash
uv run alembic revision --autogenerate -m "short description"
```

Then **always hand-edit the result**. Autogenerate is a starting point, not an answer.

- Filename and `revision` string follow the existing pattern: `00NN_snake_case`, with
  `down_revision` set to the previous head. Keep the chain linear — exactly one head.
- Include the docstring header format used by existing revisions (summary line, `Revision ID:`,
  `Revises:`).
- **Forward-only in practice**: still write a working `downgrade()` for local development, but never
  rely on it in production.
- **SQLite reality**: SQLite cannot drop or alter a column in place. Use `op.batch_alter_table(...)`
  for anything beyond `add_column` / `create_index`. `render_as_batch=True` in `env.py` covers
  autogenerated diffs, but batch mode still needs to be explicit in hand-written operations.
- **A new NOT NULL column must have a `server_default`**, or existing rows fail. See
  `0009_bottle_processing_stage`, which adds `processing_stage` with `server_default="idle"`.
- Data backfills go in the same revision as the schema change, after the DDL, using
  `op.get_bind()` / `op.execute()` — and must be **idempotent**, since bootstrap may run repeatedly.
- Never reference ORM models from a revision; describe tables inline with `sa.table`/`sa.column`.
  Models change over time; revisions must keep working against the schema as it was.

### 3. Update the bootstrap contract

- Bump `HEAD_REVISION` in `bourbonbook/migrations.py` to the new revision ID.
- **Do not** modify `EXPECTED_SCHEMA` or `BASELINE_REVISION` for a normal change. They describe the
  historical pre-Alembic legacy database, not the current schema. Changing them breaks legacy-stamp
  detection for real existing installs. Touch them only if the task is explicitly about legacy
  recognition, and say so loudly in your report.

### 4. Test all three bootstrap paths

Add tests to `tests/test_migrations.py`, following the existing naming and structure:

1. **Fresh database** reaches head, and `bootstrap_database` is idempotent when run twice.
2. **Upgrade** from the previous head with representative rows already present — assert the
   backfilled/default values on those pre-existing rows, as
   `test_bottle_processing_stage_migration_defaults_existing_rows_to_idle` does.
3. **Legacy stamp** still works and loses no data
   (`test_legacy_database_is_stamped_without_losing_catalog_data`).

Also assert the new constraint actually holds (foreign keys, uniqueness, ownership scoping) rather
than only that the column exists. Tests use `tmp_path` SQLite files — never a real database, never
`/data`.

### 5. Verify

```bash
uv run alembic heads              # must print exactly one head
uv run pytest tests/test_migrations.py
make pr-check                     # head count, tracked-file hygiene, migration tests, compose
make lint
make coverage
```

If the change touches persisted user data, also exercise the container path — `bootstrap_database`
runs before Uvicorn, so a revision that fails on startup takes the whole app down.

## Hard stops

- Never edit a revision that has already shipped. Add a new one.
- Never create a second Alembic head; `make pr-check` will fail and merges will conflict badly.
- Never drop or rename a column carrying user data without an explicit, approved migration plan
  that preserves it.
- Never modify `EXPECTED_SCHEMA` casually — it is legacy-detection state, not current schema.
- Never run migrations against `data/` or a real `.env` while testing.
